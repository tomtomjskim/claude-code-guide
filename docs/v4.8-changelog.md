# Claude Code Guide v4.8 Changelog

**Release Date**: 2026-07-28  
**Upgraded From**: v4.7

## Fixed

- Agent 호출 카운터를 공유 `/tmp/claude-hooks/agent-count-unknown`에서 분리했다.
  누락되거나 비정상인 `session_id`는 fail-open하고 카운터를 만들지 않는다.
- 유효한 session ID는 원문 대신 hash를 파일명으로 사용하고, 사용자 전용 `0700`
  runtime 디렉터리의 `0600` 파일을 `flock`으로 갱신한다. 7일이 지난 카운터는
  다음 정상 호출 때 정리한다.
- Agent 감사 로그와 Level 3 로그도 같은 private runtime 디렉터리를 기본값으로
  사용한다. Hook 테스트는 매 실행마다 별도 `mktemp` 디렉터리를 사용하므로 실제
  세션 카운터와 로그를 초기화하거나 truncate하지 않는다.
- 감사 로그의 session, agent type, description, prompt와 Level 3 command preview는
  CR/LF를 한 줄로 정규화해 위조된 추가 로그 행이 생성되지 않게 한다.
- standalone skill/hook installer는 target, project `.claude`, team/shared adapter
  destination의 모든 directory component와 file leaf symlink를 복사 전에 거부한다.
  `--force`도 symlink를 따라 외부 파일을 덮어쓰지 않는다. `--hooks`는 catalog의
  단순 이름만 허용해 path traversal로 project 밖에 파일을 만드는 경로를 차단한다.
- 비transaction `install-skills.sh --team`은 shared adapter 또는 active agent
  path 중 하나라도 이미 있으면 `--force` 없이 pair 전체를 변경하지 않는다.
- 설치 전 snapshot과 transaction journal을 XDG user state 아래에 영속 저장한다.
  skill, hook, generated settings의 모든 managed write는 같은 publish 경로를 거친다.
- transaction journal을 sibling staging directory에서 완성한 뒤 registry에
  원자 publish하고, 새로 만든 각 directory와 parent entry를 순서대로 `fsync`한다.
  target별 stable `flock`은 프로세스가 `SIGKILL`되어도 커널이 해제한다.
- durable commit 전 crash는 before-image로 rollback하고, commit-ready 이후 crash는
  새 state를 roll-forward한다. 복구 write도 destination을 다시 원자 격리·검증하고
  exclusive publish하므로 검증 직후 발생한 사용자 편집을 덮어쓰지 않는다.
- `uninstall`은 commit-ready 뒤 발생한 catch 가능한 오류와 state payload 정리 직후
  `SIGKILL`도 roll-forward한다. target별 cleanup tombstone으로 서로 다른 프로젝트의
  state cleanup이 경합하지 않게 한다.
- enterprise transaction은 Claude home의 `team/` validator package만 추적한다.
  v4.7 shared active adapter와 symlink는 별도 전역 소유 범위이므로 기존 상태를
  변경하지 않는다. 새 manifest API도 root `team` 자체가 아닌
  `claude-home:team/<path>`만 허용한다.
- `bash scripts/manage-install.sh recover --target <project>`를 추가했다. 다음
  `quick-setup`, 실제 `repair`, 실제 `uninstall`도 먼저 미완료 transaction을 복구한다.

## Migration

새 Hook을 설치한 뒤에만 session 격리가 적용된다.

```bash
bash scripts/install-hooks.sh --force <project>
```

기존 `/tmp/claude-hooks/agent-count-unknown`은 자동 삭제하지 않는다. 삭제 또는
0 초기화는 아직 구버전 Hook을 실행 중인 다른 Claude Code 세션의 누적 제한을
되돌릴 수 있다. 모든 관련 프로젝트의 Hook을 갱신하고 구버전 세션이 종료된 것을
확인하기 전에는 그대로 둔다. 새 버전은 이 legacy 파일을 읽거나 쓰지 않는다.

기존 install-state에 `claude-home:agents/*` active agent 항목이 있으면 v4.8
enterprise 재설치는 해당 destination을 수정·삭제하지 않고 새 state generation에서
소유권만 내려놓는다. 이후 `doctor`, `repair`, `uninstall`은 그 active agent를
관리하지 않는다. 새 transaction에서 active agent를 다시 managed path로 지정하는
것은 거부된다. shared adapter나 active symlink를 standalone `--team`으로 명시
교체하려는 경우에만 `--force`를 사용하며, 설치기가 기존 항목을 backup한 뒤
교체한다.

v4.8이 만든 중단 transaction은 다음 명령으로 명시 복구할 수 있다.

```bash
bash scripts/manage-install.sh recover --target <project> --json
bash scripts/manage-install.sh doctor --target <project> --json
```

pre-v4.8 설치 중단 상태는 자동 import하지 않는다. 기존 설치기는
`/tmp/<임의 디렉터리>/install-state-before`와
`<project>/.claude/.claude-code-guide-install.lock`을 사용했으므로 새 `recover`가
그 before-image를 찾을 수 없다. legacy lock의 `pid`를 확인해 해당 PID가 실제
`quick-setup.sh` 프로세스인지 확인하고, 실행 중이면 lock을 건드리지 않는다. PID가
없거나 다른 프로세스라 해도 target을 먼저 백업하고 남아 있는 legacy snapshot 또는
설치 로그를 수동 검토한 뒤에만 정확한 legacy lock directory를 제거한다. 복구 근거가
없으면 자동 삭제·강제 재설치하지 말고 수동 복원을 선택한다.

`doctor`와 `--dry-run`은 managed target 파일과 install-state를 바꾸지 않는다.
동시 lifecycle 작업을 막기 위해 XDG state home에는 target별 lock directory/file이
생성되거나 mode가 보정될 수 있다. 실제 `repair`와 `uninstall`은 미완료 transaction을
먼저 복구한 뒤 요청 작업을 수행한다.

## Support Boundary

crash consistency 보장 범위는 Python `fcntl`, `flock`, same-filesystem
rename/link, file·directory `fsync`를 제공하는 local POSIX filesystem이다.
네트워크 filesystem, Windows native filesystem, 저장장치/파일시스템 자체 손상,
악의적인 동일 사용자 프로세스는 보장 범위 밖이다. 손상되거나 예상 metadata와
일치하지 않는 journal·destination은 자동 덮어쓰지 않고 fail-closed한다.

## Validation

```bash
python3 -m unittest discover -s scripts/tests -p 'test_*.py' -v
bash hooks/tests/run-tests.sh
bash scripts/validate-repository.sh
```

실제 `SIGKILL` fault injection은 generated publish capture, 전체 quick setup,
state commit-ready, repair capture, uninstall state unlink와 state payload cleanup
경계를 검증한다. 별도 fault test는 capture 직전 및 recovery 검증 직후의 사용자
편집과 catch 가능한 post-commit 오류를 검증한다.
